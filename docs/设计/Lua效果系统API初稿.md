### 0.2 Effect 调度理解

以下是 Agent 与 txym 对当前规则的理解，后续设计接口时继续核对：

1. 游戏规则中的 Effect 不并行执行。同一父节点下已经确定顺序的子 Effect 依次进入执行和结算；前一个兄弟节点完成后，下一个兄弟节点才能执行。
2. 一个 Effect 完成本身工作后，要么进入成功完成态，要么进入规则失败态，要么创建子节点并等待尚未结束的阻塞型子节点。成功和规则失败都是终态；只要子节点已经进入任一终态，就不再阻塞父节点。
3. “玩家可以选择先后顺序”不称为并发执行，而称为“无序候选集合”。玩家作出选择后，被选中的候选转化为当前有序执行节点。
4. 玩家行动窗口中的主要行动和快速行动可以作为无序候选挂在对应主链节点下，但玩家每次只选择并执行一个。
5. `指令姐`的“战术行动”可能同时出现在特殊行动入口和快速行动入口中；两个入口必须复用同一个挂在玩家身上的“是否已使用”状态。卡牌正式名称和具体入口仍待牌面核对。
6. 收尾阶段仍按本回合玩家顺序推进。某个玩家的原始收尾 Effect 直接挂在该玩家的收尾窗口节点下；同一玩家有多个收尾 Effect 时，它们先作为无序候选，由该玩家决定执行顺序。
7. 多名玩家可任意顺序提交的规则任务使用“开放玩家任务组”。它可以同时展示多个玩家待办，但 Host 仍逐条提交状态；它不改变第 1 条所述的单条规则结算顺序。

### 0.3 永续内容与可选行动池

- 角色牌永续和授勋卡永续当前理解为可用状态及 UI 表现，而不是在获得时立即挂入一条长期未完成的 Effect。
- 玩家实际选择使用永续能力时，再由对应操作形成 Event 并触发 Lua。
- 永续退出时需要同步处理可用状态，例如从玩家可选行动池中移除对应入口。
- 永续能力是否还需要持续规则记录，以及记录位于玩家状态、卡牌实例还是独立规则状态中，留到具体 API 阶段确认。

### 0.4 Lua 的运行期触发来源

当前理解是：Lua 在对局运行期由明确 Event 触发。Event 的常见来源包括：

- 玩家 UI 操作经 C# 命令校验后直接形成的 Event；
- 玩家操作引发某项 Effect，并在该 Effect 结算前后间接形成的 Event；
- 回合主链等系统流程形成的 Event。

UI 操作本身不能绕过 C# 直接调用 Lua。哪些 Event 属于高频通用 Event，哪些只为少数卡面提供，需要在第 6、7 节逐项登记。

### 0.5 角色牌双发链待统一

当前角色牌双发的主要特殊情况是阿米娅。按目前对规则书的理解，顺序应为：

```text
开始使用角色牌
  → 在单发选择之前使用阿米娅计谋
  → 将本次使用改为双发
  → 完成本次角色牌使用
```

普通快速行动使用角色牌时，角色牌节点连接在快速行动节点下，其子节点包含策略或计谋。加入阿米娅后，如果先挂阿米娅再挂策略和计谋，会形成不同的 Effect 链扩展方式。

设计目标是让所有实际双发最终使用同一种链结构。第 27 条“改变角色牌双发限制”负责表达禁用、单发、可双发以及“下一次使用改为双发”等状态；具体链结构仍待固有效果链和 API 共同确定。

#### 1.1.1 Effect式

`Effect式`不是条件式、选择式和次数式的统称，也不是一种独立的卡面最小 Effect。它表示一个有序的 Effect 描述列表；列表中的每一项都由某个卡面最小 Effect 或固有效果链的构造函数产生。

当前关系为：

```text
Event 调用 Lua 处理函数
  → Lua 返回由一个或多个 Effect 描述组成的 Effect式
  → C# 将每个 Effect 描述分别建立为当前结算节点的子节点
  → 子节点按列表顺序执行，并在进入成功或失败终态前阻塞当前结算节点完成

条件式 / 选择式 / 次数式
  → 本身属于卡面最小 Effect
  → 构造函数参数中可以嵌套一个或多个 Effect式
```

Effect式本身没有独立的 `effectTypeId`，也不会额外生成一个“Effect式节点”。最外层 Effect式就是 Lua 处理函数返回的连续数组；数组中每项直接成为一个子 Effect 节点。条件式、选择式和次数式自身仍各生成一个节点，它们参数中的嵌套 Effect式只在对应分支或次数实际执行时再生成更深一层子节点。

普通 Effect 被玩家主动放弃后进入 `Failed`，失败属于已结算的终态，不再阻塞父节点，Effect式继续处理下一个兄弟节点；条件式是明确例外，其左侧失败时不会创建右侧 Effect式。其他需要“前项失败则后项也不执行”的牌面组合，应使用条件式表达，而不是依赖普通数组的隐含行为。

#### 1.1.2 Lua 添加 Effect 的挂载位置

| 挂载位置 | 当前含义 | 顺序或阻塞 | 关键约束 |
| --- | --- | --- | --- |
| 当前结算节点 | 卡面能力的 `current` 处理函数返回 Effect式；每一项分别成为当前结算节点的有序子 Effect | 默认阻塞当前结算节点完成 | 父节点由 Event 调用上下文确定，Lua 不填写父节点 ID |
| 本回合该玩家的收尾窗口节点 | 卡面能力的 `playerCleanup` 处理函数在对应玩家收尾窗口被 C# 调用，返回项挂在该玩家收尾节点下 | 同一玩家的多个收尾 Effect 可组成有限效果轮，由玩家决定顺序 | `activationPolicy` 必须区分持续有效与本回合登记一次 |
| 最终分数结算节点 | 卡面能力的 `finalScoring` 处理函数在最终计分时被 C# 调用，返回项挂在对应计分节点下 | 按最终计分的规则顺序执行 | `scoringScope` 和 `orderPolicy` 必须能确定作用对象与稳定顺序 |
| 其他规则时机 | 卡面通过 `eventSubscriptions` 订阅明确 Event，处理函数返回项挂在该 Event 的当前结算节点下 | 使用该 Event 的响应排序和默认阻塞规则 | Event 类型、过滤条件和响应顺序 |

三个固定挂载区写在卡面能力定义中，不写在每个 `EffectSpec` 上。每个处理函数本身都只返回 Effect式；实际父节点由 C# 根据处理函数所属挂载区解析。其他时机统一通过 Event 进入，仍不允许 Lua 用任意节点 ID 改写 Effect 树。

#### 1.2.3 活动 UI

活动 UI 指玩家可以主动打开或关闭，但打开面板本身不代表已经提交规则操作的界面。当前包括：

- 企业面板；
- 设施供应区；
- 永续干员牌面板；
- 其他后续补充的卡面浏览面板。

面板内的具体按钮或拖拽只有通过命令入口并经 C# 校验后，才会转化为玩家主动唤起的交互或 Event。

补充说明：

- 次数选择 UI 可能同时服务于出售资源、获得资源和选择式的次数分配，是否使用同一个交互 API 待确认。
- “结算事件”当前同时包含 UI 选择和产生奖励 Effect式，可能需要拆成最小交互与固有效果链两层。
- 表中的中文名称用于识别交互，不等于最终 API 名称或完整接口描述。

## 2. Lua 卡面定义 API

### 2.1 定义阶段与运行阶段

C# 需要提供可校验的卡面定义结构、Lua 注册入口和内容目录。Lua 使用这些结构声明具体卡面，不要求 C# 硬编码每一张具体卡牌。

卡面定义加载不由 `RuleEvent` 触发，因为它属于对局开始前的内容注册阶段，不属于一次规则结算：

```text
内容加载阶段
  → C# 创建受限 Lua 定义环境
  → Lua 返回具体卡面定义
  → C# 校验并建立只读内容目录和 Event 订阅索引
  → 对局绑定本次内容版本

对局运行阶段
  → C# 形成 RuleEvent
  → EventBus 找到已注册的具体卡面 Lua
  → Lua 生成 Effect式或其他受支持请求
```

因此，“Event 是 Lua 的唯一规则入口”只约束对局运行阶段。定义阶段的 Lua 只能声明静态内容，不能读取或修改某局 `GameState`、创建实际 Effect 节点、请求 UI 或使用未受控随机数。

### 2.2 C# 需要提供的内容定义

这里的“定义类型”表示 C# 必须提供相应的数据契约、注册和校验能力；实现时可以使用共同基类加类型字段，不要求每种内容都必须成为完全独立的 C# 类。

| 内容类型 | C# 提供的逻辑定义 | Lua 负责填写的内容 | 玩家标记区 | 当前决定 |
| --- | --- | --- | --- | --- |
| 城市样式牌 | `CityStyleCardDefinition` | 具体牌面、标记区、能力和 Effect式 | 有 | 需要定义 |
| 企业板 | `EnterpriseBoardDefinition` | 合作等级、奖励、解锁内容、标记区和企业特效 | 有 | 需要定义 |
| 角色牌 | `CharacterCardDefinition` | 策略、计谋、标记区和对应处理器 | 有 | 需要定义 |
| 企业家能力牌 | `EntrepreneurAbilityCardDefinition` | 能力、标记区、触发条件和对应处理器 | 有 | 需要定义 |
| 企业家回合卡 | `EntrepreneurRoundCardDefinition` | 回合内容、标记区、触发条件和对应处理器 | 有 | 需要定义 |
| 设施牌 | `FacilityCardDefinition` | 费用、分数、标签、入场效果和其他牌面能力 | 当前未指定 | 需要定义 |
| 科室板 | `DepartmentBoardDefinition` | 科室板状态、区域和能力 | 待确认 | 可能不需要独立定义 |
| 牌堆 | `DeckDefinition` | 可包含内容、初始化和区域规则 | 不适用 | 可以考虑定义 |

“当前未指定”表示尚未确认这种内容是否普遍拥有玩家标记区，不等于禁止个别卡面将玩家标记作为目标。

### 2.3 内容共同定义

以下只作为待填写的数据壳子。字段是否放在 Lua 定义中，等实际卡面录入后再收敛：

```text
LuaContentDefinition
├─ definitionId
├─ contentType
├─ version
├─ displayNameKey
├─ artworkId
├─ tags
├─ playerMarkerZones[]
├─ abilities[]
│  ├─ effectHandlers
│  └─ eventSubscriptions[]
├─ effectExpressions[]
└─ deckReferences[]
```

共同字段说明：

| 字段 | 用途 | 是否必须 | 待确认项 |
| --- | --- | --- | --- |
| `definitionId` | 内容包内稳定标识 | 是 | 命名和扩展命名空间 |
| `contentType` | 区分城市样式牌、企业板等定义类型 | 是 | 枚举范围 |
| `version` | 对局恢复时绑定相同规则版本 | 是 | 版本号与内容哈希关系 |
| `displayNameKey` | 引用本地化显示名称 | 待定 | 是否允许 Lua 直接提供默认名称 |
| `artworkId` | 引用 Unity 侧美术资源 | 待定 | 资源不存在时的处理 |
| `tags` | 提供受控分类和候选过滤 | 待定 | 标签注册表 |
| `playerMarkerZones` | 声明卡面上的玩家标记区 | 按内容类型 | 见第 2.4 节 |
| `abilities` | 声明卡面能力和稳定能力 ID | 按卡面 | 主动、被动和持续能力结构 |
| `abilities[].effectHandlers` | 声明当前结算、玩家收尾和最终计分三个固定处理区 | 按能力 | 激活方式、作用玩家和排序，见第 2.5 节 |
| `abilities[].eventSubscriptions` | 声明三个固定处理区以外需要监听的 Event | 按能力 | 实例何时启用或停用订阅 |
| `effectExpressions` | 声明可以生成的 Effect式 | 按能力 | 引用、内联和复用方式 |
| `deckReferences` | 声明所属或关联牌堆 | 待定 | 是否改由牌堆单向引用卡牌 |

具体卡面实例的所属玩家、所在区域、玩家标记占用、是否已使用等动态状态属于 `GameState`，不能写回 Lua 卡面定义。

### 2.4 玩家标记区

城市样式牌、企业板、角色牌、企业家能力牌和企业家回合卡都可以声明玩家标记区。C# 至少需要提供一种通用的玩家标记区定义：

```text
PlayerMarkerZoneDefinition
├─ zoneId
├─ zoneKind
├─ capacity
├─ allowedMarkerOwners
├─ selectionTags[]
├─ initialState
└─ displayAnchorId
```

字段的准确含义留到录入具体卡面时确认。最低要求是：同一卡面定义内的 `zoneId` 唯一，容量和允许进入的玩家标记必须可以由 C# 校验。

玩家标记区需要成为最小 UI 交互可以返回的一类卡面选项。运行期选择的不是静态 `PlayerMarkerZoneDefinition`，而是本局具体卡牌或板块实例上的区域引用：

```text
PlayerMarkerZoneRef
├─ contentInstanceId
├─ contentDefinitionId
├─ zoneId
└─ currentMarkerState
```

选择流程暂定为：

```text
Lua 或固有效果链提出玩家标记区选择请求
  → C# 根据定义目录和当前 GameState 生成候选 PlayerMarkerZoneRef
  → UI 显示卡面或板块及其可选玩家标记区
  → 玩家选择一个或多个区域引用
  → C# 复验内容实例、zoneId、容量、所有权和当前状态
  → 记录答案并形成后续 Event
```

Lua 只能使用稳定的内容实例 ID 和 `zoneId` 指定或过滤区域，不能保存 Unity 场景对象、坐标或 UI 控件引用。实际放置、移动和移除玩家标记仍需调用对应的卡面最小 Effect。

以下细节待填写具体卡面后确认：

- 玩家标记区是否包含单个槽位和多槽位两种结构；
- 区域是否区分可放置、计数、次数、锁定和已使用等用途；
- 某些区域能否只接受卡牌所有者或指定玩家的标记；
- UI 选择结果返回整个区域，还是必须返回区域内具体槽位；
- 企业合作等级轨道是否复用该结构，还是使用独立的等级轨道定义。

### 2.5 卡面能力的三个固定 Effect 处理区

每个卡面能力可以声明以下三个处理区。这里保存的是稳定 Lua 处理函数引用和激活规则，不是在内容加载阶段创建实际 Effect 节点。“挂到某个区域”表示 C# 到达该规则时点后形成 Event、调用处理函数，再把函数返回的 Effect式编译成该时点节点的子节点：

```text
EffectHandlerSlots
├─ current
│  └─ handler
├─ playerCleanup
│  ├─ handler
│  ├─ activationPolicy
│  ├─ playerScope
│  ├─ cancelPolicy
│  └─ orderPolicy
└─ finalScoring
   ├─ handler
   ├─ activationPolicy
   ├─ scoringScope
   ├─ cancelPolicy
   └─ orderPolicy
```

| 处理区 | Lua 定义字段 | C# 调用时机 | 返回 Effect式挂载位置 |
| --- | --- | --- | --- |
| 当前结算 | `effectHandlers.current` | 该能力被定向 Event 唤起，且来源节点仍处于结算中 | Event 上下文指定的当前结算节点 |
| 玩家收尾 | `effectHandlers.playerCleanup` | 对应玩家的收尾窗口 Event 形成，且该能力满足激活规则 | 该玩家收尾节点；多个候选需要排序时由有限效果轮承载 |
| 最终计分 | `effectHandlers.finalScoring` | 最终计分进入该玩家或该卡面对应的计分项 | 对应最终计分节点 |

Lua 定义示意：

```lua
{
    abilityId = "ability.example",
    effectHandlers = {
        current = {
            handler = "on_resolve"
        },
        playerCleanup = {
            handler = "on_player_cleanup",
            activationPolicy = "after_resolve_once",
            playerScope = "ability_owner"
        },
        finalScoring = {
            handler = "on_final_scoring",
            activationPolicy = "while_active",
            scoringScope = "ability_owner"
        }
    },
    eventSubscriptions = {
        -- 其他非固定时机在这里显式订阅 Event
    }
}
```

`activationPolicy` 第一版至少区分：

- `while_active`：只要该卡面实例当前处于允许其能力生效的区域，每次进入对应时机都调用。
- `after_resolve_once`：当前能力成功结算后登记一次，在本回合收尾或最终计分的指定窗口调用一次后消费。

`cancelPolicy` 决定来源卡面离场、能力失效或目标玩家离开游戏后，已经登记的一次性处理器是继续执行还是取消，不能由 C# 猜测。

`after_resolve_once` 不能保存 Lua 闭包或局部变量。C# 必须在来源 Effect 的记录中登记可序列化的 `TimingHandlerBinding`，记录卡面实例、能力 ID、来源 Effect、目标窗口、作用玩家和已经确认的稳定引用；到达目标窗口时再形成 Event 并调用对应处理函数。`TimingHandlerRegistry` 只是根据 Effect 链和当前卡面状态建立的可重建索引，不是另一份权威游戏状态。

三个固定处理区在运行时仍由对应的内核 Event 唤起，但卡面作者不需要为它们手写通用 Event 订阅和过滤条件。三个固定区之外的触发，例如其他玩家获得资源后、某企业特效完成后或某类 Effect 结算前，继续使用 `eventSubscriptions`。

### 2.7 科室板与牌堆

科室板是否需要独立的 `DepartmentBoardDefinition` 暂不决定。若科室板只作为某家企业特效的内部状态和选项，可以先由对应企业定义引用；只有当它具有可复用区域、独立能力、独立订阅或需要作为通用 UI 目标时，再提升为独立内容定义。

牌堆可以考虑使用通用 `DeckDefinition`。它描述的是内容容器和区域规则，不是某张卡面：

```text
DeckDefinition
├─ deckId
├─ acceptedContentTypes[]
├─ setupComposition
├─ drawZone
├─ discardZone
├─ candidateZone
├─ visibility
└─ shufflePolicy
```

牌堆定义不能保存某局的实际顺序。实际卡牌实例、当前顺序、抽取结果和洗混结果属于 `GameState` 与 Effect 链。

### 2.8 内容加载校验

C# 加载 Lua 卡面定义时至少检查：

- `definitionId` 在当前内容集合中唯一；
- 内容类型、版本和引用字段合法；
- 同一卡面内的能力 ID 和玩家标记区 `zoneId` 唯一；
- 三个固定处理区引用的 Lua 处理函数存在，`activationPolicy`、作用范围和排序策略合法；
- `eventSubscriptions` 引用的 Event 存在，处理函数返回类型与 Event 的 `responseKind` 一致；普通规则 Event 只能返回 `EffectSpec[]`，候选集 Event 只能返回 `CandidatePatch[]`；
- `CandidateSetBuilding` 订阅声明的 `candidateKindFilter`、补丁操作和订阅顺序字段合法；非候选 Event 不得声明候选补丁响应；
- 玩家标记区容量、允许所有者和标签格式合法；
- 引用的 Effect、Effect式、Event、Lua 模块和处理函数存在；
- 牌堆引用的内容类型符合约束；
- 扩展替换既有定义时具有显式替换关系，不依赖加载顺序覆盖；
- 对局记录本次内容目录的版本或哈希，恢复时不能静默换用不同卡面定义。

## 3. Lua 运行时 API

### 3.1 API 分类与共同边界

Lua 中的“类”实际表现为 C# 注入的只读命名空间表或受限 `userdata`，不暴露 CLR 对象，也不等同于 Lua 自带的 `_G`。第一版运行时 API 分为五类：

| API 类 | 职责 | 是否读取本局状态 | 是否可以产生规则变化 | C# 提供者 |
| --- | --- | --- | --- | --- |
| `Global` | 查询地图、公共区域和内容定义等世界数据 | 是，限公开地图状态 | 否 | `GlobalApiFacade` |
| `GameData` | 查询当前对局的全局状态与启用内容 | 是 | 否 | `GameDataApiFacade` |
| `PlayerData` | 查询指定玩家的公开状态和调用者有权看到的私有状态 | 是 | 否 | `PlayerDataApiFacade` |
| `Effect` | 为每种 Effect 构造一个 `EffectSpec`；Lua 将一个或多个 `EffectSpec` 作为 Effect式返回 | 只接收查询结果中的稳定引用 | 是，但只形成待 C# 校验的子节点描述 | `EffectApiFacade` |
| `Candidate` | 在候选集构建 Event 中构造增量候选补丁 | 是，只读本次候选快照 | 否；只能改变当前 Effect 的可选范围 | `CandidateApiFacade` |

共同约束：

- `Global`、`GameData`、`PlayerData` 只返回当前 Lua 调用上下文中的只读快照或稳定引用。Lua 修改返回的普通 table 不会修改 C# 状态。
- Lua 不能取得 `GameState`、Unity 场景对象、组件、坐标对象或可写集合的引用。
- 所有查询都绑定本次 `RuleEvent` 的 `stateRevision`。Lua 处理函数结束后，API 门面失效；保存门面并在之后调用必须报错。
- 查询结果只用于构造返回的 `EffectSpec`。C# 在 Effect 真正执行前仍会根据最新权威状态复验，不能把“Lua 查询时合法”当作最终合法性。
- 卡面脚本不能通过查询读取本不应公开的手牌、盖放牌或其他隐藏信息。Host 知道数据不等于当前 Lua 处理器有权读取。
- 运行期 Lua 只能由 `RuleEvent` 进入。查询 API 本身不产生 Event，也不创建 UI。
- 所有枚举、内容、地图对象和规则主体都使用稳定 ID；本地化名称只用于表现，不能作为查询键或 Effect 参数。
- Event 会声明返回契约。普通规则 Event 只能返回 `EffectSpec[]`；候选集构建 Event 只能返回 `CandidatePatch[]`，两者不能混用。

### 3.2 共同引用与快照

Lua API 不在多个接口中传递完整对象，而是传递可序列化的引用。第一版至少需要：

```text
PlayerRef
└─ playerId

RuleSubjectRef
├─ subjectType = player / enterprise / character / none
├─ instanceId
├─ definitionId
└─ playerId

LocationRef / RouteRef / RegionRef
└─ 对应稳定 ID

InfluenceSlotRef
├─ slotId
├─ slotKind = location / route
├─ locationId 或 routeId
└─ slotIndex

InfluenceRef
├─ influenceId
├─ ownerSubject = RuleSubjectRef，可为空归属
├─ sourceRef
└─ slot = InfluenceSlotRef

ContentRef
├─ contentType
├─ definitionId
└─ instanceId
```

`RuleSubjectRef` 用于处理不一定属于玩家的影响力和能力来源。企业、角色或无归属影响力不能伪造一个 `playerId`；需要判断与某玩家的关系时，C# 按具体规则或调用方传入的合法筛选条件判断。

快照可以比引用包含更多只读字段，例如资源数量、地块开放状态或设施牌朝向。任何 Effect 参数最终都必须被 C# 归一化为稳定引用和基础值，不能把整份 Lua 快照原样存入 Effect 链。

### 3.3 `Global`：地图与公共世界查询

`Global` 第一版分为 `Global.Map` 与 `Global.Content`。地图查询同时覆盖静态拓扑和本局公开地图状态；内容查询只返回已通过内容加载校验的定义或实例。

| Lua API | 返回 | 规则含义 | C# 处理 |
| --- | --- | --- | --- |
| `Global.Map.GetMap()` | `MapSnapshot` | 当前使用的地图及其地块、航道、区块 ID | 从本局 `mapId` 解析不可变地图定义，再叠加公开运行状态 |
| `Global.Map.GetLocation(locationId)` | `LocationSnapshot` 或 `nil` | 地块定义、开放和探索状态、资源点指示物、停靠城市 | 校验 ID；合并 `MapLocationDefinition` 与 `MapRuntimeState` 投影 |
| `Global.Map.GetRoute(routeId)` | `RouteSnapshot` 或 `nil` | 航道端点、覆盖地块、基础费用、公路状态 | 校验 ID；合并 `MapRouteDefinition` 与公路运行状态 |
| `Global.Map.GetRegion(regionId)` | `RegionSnapshot` 或 `nil` | 区块包含的地块、航道和计分值 | 从地图定义生成只读快照 |
| `Global.Map.GetConnectedLocations(locationId)` | `LocationRef[]` | 与指定地块直接相邻的地块 | 由 C# 地图查询服务计算，不让 Lua 自行解释地图资产 |
| `Global.Map.GetRoutesBetween(fromId, toId)` | `RouteRef[]` | 直接连接两个地块的航道 | 返回稳定航道引用；不在这里判断某项行动是否合法 |
| `Global.Map.GetInfluenceSlot(slotId)` | `InfluenceSlotSnapshot` 或 `nil` | 槽位定义及当前占用 | 使用统一槽位解析器校验槽位编号和所属地块或航道 |
| `Global.Map.FindInfluences(filter)` | `InfluenceRef[]` | 按归属主体、地块、航道或槽位集合查询影响力 | C# 只接受白名单筛选字段并设置最大返回数量；归属主体允许为空 |
| `Global.Map.GetResourcePoint(locationId)` | `ResourcePointSnapshot` 或 `nil` | 已放置资源点指示物时返回资源类型和数量 | 未探索或没有指示物时返回 `nil` |
| `Global.Map.GetCitiesAt(locationId)` | `PlayerRef[]` | 停靠在该地块的移动城市 | 从玩家城市位置生成公开投影 |
| `Global.Map.IsRoad(routeId)` | `boolean` | 航道是否已经被公路覆盖 | 读取公开公路状态 |
| `Global.Content.GetDefinition(definitionId)` | `ContentDefinitionSnapshot` 或 `nil` | 查询当前对局绑定版本中的卡面定义 | 只读内容目录查询；不返回 Lua 函数和内部 C# 对象 |
| `Global.Content.GetInstance(instanceId)` | `ContentInstanceSnapshot` 或 `nil` | 查询本局公共可见内容实例 | 应用可见性过滤并附带 `definitionId` |
| `Global.Content.FindInstances(filter)` | `ContentRef[]` | 按内容类型、定义 ID、区域或标签查找公开实例 | C# 校验筛选字段、可见性和返回数量上限 |

`Global.Map` 只描述地图事实，不代替具体 Effect 的规则校验。例如相邻地块可以由 `GetConnectedLocations` 查到，但能否移动城市仍由“移动城市”效果链根据开放状态、停靠情况和调用参数复验。

### 3.6 `Effect`：子 Effect 构造与返回

`Effect` 的职责不是让 Lua 主动提交或挂载节点，而是为每个卡面最小 Effect 和固有效果链提供对应构造函数。每次调用构造函数只生成一个声明式 `EffectSpec`，不读取或修改 C# 状态，也不会立即创建 Effect 节点。

Event 调用 Lua 处理函数时，C# 已经在 `LuaInvocationContext` 中确定“当前结算节点”。Lua 处理函数只需返回一个连续数组：

```lua
return {
    Effect.GainResource({ ... }),
    Effect.PlaceInfluence({ ... }),
    Effect.GainScore({ ... })
}
```

这个数组就是最外层 Effect式。C# 将数组中三个 `EffectSpec` 分别建立为当前结算节点的三个子节点，保持数组顺序；前一个子节点进入成功或失败终态后才执行下一个，三个子节点在终态前默认都阻塞当前结算节点完成。

统一规则如下：

- 每个 `Effect.*` 构造函数返回且只返回一个 `EffectSpec`，对应将来的一棵 Effect 节点。
- Lua 处理函数必须返回连续整数下标的 `EffectSpec[]`；只返回一个 Effect 时也使用单元素数组。
- 返回空数组 `{}` 表示本次 Event 不产生子 Effect。返回 `nil`、稀疏数组、普通键值表或混入非 `EffectSpec` 的数组视为脚本错误。
- 同一次 Lua 返回的全部 `EffectSpec` 先整体校验，全部合法后才一起加入树；不能只挂入其中一部分。
- Lua 不填写 `parentEffectId`、`ownerEffectId`、`nodeId`、`blocking` 或任意挂载目标，以上信息全部由 C# 的 Event 调用上下文和默认规则确定。
- 构造函数参数统一使用具名 table。C# 保存的是规范化后的参数，不保存 Lua table 本身。

多数 Effect 共用一组可选执行字段，而不为每个接口分别发明“是否执行”参数：

| 共同字段 | 类型 | 默认值 | 含义 |
| --- | --- | --- | --- |
| `allowDecline` | `boolean` | `false` | 为真时，在节点产生随机结果、公开隐藏信息或提交状态之前，为指定玩家提供“放弃”按钮 |
| `decisionPlayer` | `PlayerRef` | Effect 的执行玩家 | `allowDecline = true` 时有权点击放弃按钮的玩家 |
| `declinePromptKey` | `string` | 通用提示 | UI 使用的本地化提示键，不改变规则语义 |
| `unavailablePolicy` | 稳定枚举 | 由具体 Effect 定义 | 当前无法执行时采用哪种规则失败原因或“合法无变化”；它与玩家主动放弃不同 |

玩家点击放弃按钮后，UI 向 Host 提交 `DeclineEffect(effectId)`；Host 校验决定玩家和节点时点后，将节点记录为 `Failed`，并写入 `failureReason = player_declined`。`Failed` 是完成态，不再阻塞父节点；它不提交该 Effect 的规则状态，也不产生该 Effect 的成功语义 Event。通用 `EffectCompleted` 可以携带 `outcome = failed`。条件式的左侧失败时不创建右侧。

条件式、选择式和次数式同样是卡面最小 Effect，因此也各自拥有构造函数，而不是纯结构辅助函数：

| Lua API | 返回节点 | 嵌套 Effect式 |
| --- | --- | --- |
| `Effect.Condition(args)` | 一个条件式节点 | `leftEffects` 和 `rightEffects` 各自是 `EffectSpec[]` |
| `Effect.Choice(args)` | 一个选择式节点 | 每个选项携带一个 `EffectSpec[]` |
| `Effect.Repeat(args)` | 一个次数式节点 | `body` 是一个 `EffectSpec[]` |

这些嵌套列表在 Lua 返回时先完成结构校验，但不会立刻全部建立成运行节点。例如选择式只在玩家选定某个选项后，才把该选项的 Effect式建立为选择式节点的子节点。

`candidateScope` 是调用方给出的范围约束，不是 Lua 已经算好的最终合法集。只要接口需要选择地图位置、卡牌或规则主体，C# 都先按对应 `candidatePolicy` 建立候选池上限和基础候选，再执行第 3.7 节的候选修正流程。

一个事件处理器的完整示例：

```lua
function on_ability_activated(event)
    local player = PlayerData.Get(event.playerId)
    local target = Global.Map.GetInfluenceSlot(event.payload.slotId)

    return {
        Effect.GainResource({
            player = player.ref,
            resourceId = "gold_voucher",
            amount = 2
        }),
        Effect.PlaceInfluence({
            executingPlayer = player.ref,
            influenceSource = { kind = "player_supply", playerId = player.playerId },
            ownerSubject = { subjectType = "player", playerId = player.playerId },
            allowedSlotIds = { target.slotId }
        })
    }
end
```

例如上面的两个返回项会成为同一当前结算节点下的两个有序子节点，而不是先生成一个额外的 `Sequence` 节点。

掷骰、抽牌、选择结果等运行时结果不能依赖 Lua 局部变量等待后续使用。对应 Effect 完成后由 C# 形成新的 `RuleEvent`，下一次 Lua 处理函数从 Event payload 读取结果并返回新一组子 Effect。

玩家收尾和最终计分也不通过普通 Effect 构造函数填写任意目标 ID。它们由卡面能力定义中的固定处理区声明；C# 在对应时点形成 Event、调用处理函数，并把返回列表挂到当前收尾或计分节点。其他规则时机继续通过显式 `eventSubscriptions` 进入相同流程。

### 3.7 `Candidate`：可选范围的增量修正

城市移动目的地、影响力放置槽位等候选，不能完全由 Lua 生成。C# 先根据 Effect 类型、地图拓扑和不可违背的规则构建“候选池上限”和“基础候选”，再形成 `CandidateSetBuilding` Event。显式订阅该 Event 的 Lua 能力只返回增量补丁：

```lua
function block_frozen_location(event)
    if event.payload.candidateKind ~= "city_move_destination" then
        return {}
    end

    return {
        Candidate.Remove({
            ids = { "location.red.03" },
            reasonCode = "entrepreneur.frozen_location"
        })
    }
end
```

第一版接口：

| Lua API | 参数 | 作用 |
| --- | --- | --- |
| `Candidate.Add(args)` | `ids[]`、`reasonCode` | 把候选池上限内、当前未入选的 ID 加入当前集合；允许加入被普通基础规则排除、但未被硬约束排除的项目 |
| `Candidate.Remove(args)` | `ids[]`、`reasonCode` | 从当前集合移除指定 ID |
| `Candidate.Intersect(args)` | `ids[]`、`reasonCode` | 当前集合只保留给定 ID，用于整组范围收窄 |

候选解析使用三层数据：

```text
CandidateSetDraft
├─ candidateSetId
├─ candidateKind
├─ sourceEffectId
├─ executingPlayerId
├─ candidatePoolIds    # 候选池上限：通过硬约束、允许被 Lua 考虑的全部项目
├─ defaultCandidateIds # 基础候选：按普通规则默认可以选择的项目
├─ currentIds          # 当前候选：已应用前序 Lua 补丁后的项目
└─ context             # 地块、航道、来源槽位等稳定引用
```

三个集合可以简单理解为：

- `candidatePoolIds` 是“最多可以考虑哪些”。不存在的对象、错误类型、越权目标等不会进入这里，Lua 永远不能越过它。
- `defaultCandidateIds` 是“没有卡面修正规则时，UI 默认会显示哪些”，它是 `currentIds` 的初始值。
- `currentIds` 是“应用所有 Lua 增加、移除和求交补丁后，最终交给 UI 的哪些”。

例如普通城市移动时，候选池可以包含本次移动模式允许考虑的地图地块；基础候选只包含相邻、已开放且没有对手移动城市的地块。某张牌允许驶入一个通常不合法但仍在候选池中的地块时，用 `Candidate.Add` 加入；某个企业家静止一个资源点时，用 `Candidate.Remove` 移除。最终 UI 只显示 `currentIds`。

执行规则：

1. C# 先按 Effect 注册的 `candidatePolicy` 生成 `candidatePoolIds` 和 `defaultCandidateIds`，再令 `currentIds = defaultCandidateIds`。
2. `CandidateSetBuilding` 按稳定订阅顺序调用 Lua；每个处理器看到前序补丁后的 `currentIds`。
3. C# 依次应用 `Add`、`Remove` 或 `Intersect`，并记录补丁来源、理由和顺序。
4. `Add` 可以绕过 `defaultCandidateIds` 所表达的普通基础规则，但只能加入 `candidatePoolIds` 中的项目，不能加入不存在、类型错误或被不可覆盖硬约束排除的目标。补丁必须记录稳定 `reasonCode`，使 Host 重建候选池和基础候选后可以按相同订阅顺序重放并复核。
5. 最终集合写入 `InteractionRequest`。提交固定目标的 Effect 也必须让单项目标经过相同解析，不能绕过卡面限制。
6. 玩家回答后，C# 基于最新 `stateRevision` 重建并再次应用补丁；目标不再合法时拒绝本次答案并刷新交互，不执行部分状态提交。

`CandidateSetBuilding` 是同步的纯候选 Event。其处理器不能返回 `EffectSpec`、创建 UI、产生随机数或修改状态。Lua 返回值只在 C# 校验并规范化后成为 `CandidatePatchRecord`，随交互节点进入 Effect 链；恢复时复用已记录的最终候选集和补丁，不保存 Lua 调用现场。

第一阶段优先接入以下 `candidateKind`：

| `candidateKind` | 基础集合来源 | 典型 Lua 修正 |
| --- | --- | --- |
| `city_move_destination` | 指定移动模式下的相邻地块、开放状态与城市占用规则 | 移除被“静止”或被卡面禁止驶入的资源点 |
| `influence_placement_slot` | 指定放置模式下的空槽、资源点、对手城市与公路规则 | 移除某些区块、地块或航道上的槽位 |
| `influence_move_source` | 符合归属和当前 Effect 范围的影响力 | 禁止移动受某能力锁定的影响力 |
| `influence_move_destination` | 当前来源影响力在指定移动模式下可到达的槽位 | 禁止进入某类区域；根据前序选择动态收窄 |
| `influence_removal_target` | 符合归属筛选和范围的现有影响力 | 保护某来源或某区域的影响力不被移除 |
| `facility_supply_card` | 当前公开设施供应区中的可用设施牌 | 卡面禁止或限定某颜色、费用、标签的设施牌 |

如果多个补丁对同一个 ID 先移除后添加，按 Event 的稳定处理器顺序依次应用，后执行的补丁得到最终结果；任何补丁都不能突破 `candidatePoolIds`。稳定顺序由显式订阅优先级、内容实例 ID、能力 ID 和订阅 ID 组成，不能依赖 Lua 文件或模块加载顺序。

### 3.8 单项 Effect 实现合同模板

## 4. C# 内核处理说明

### 4.1 运行时组成

C# 侧建议将 Lua 运行时拆成以下职责，不让脚本绑定现有 `GameState` 或具体命令处理器：

```text
LuaRuntimeHost
├─ LuaEventDispatcher
├─ TimingHandlerRegistry
├─ LuaInvocationContextFactory
├─ LuaApiHost
│  ├─ GlobalApiFacade
│  │  ├─ MapQueryFacade
│  │  └─ ContentQueryFacade
│  ├─ GameDataApiFacade
│  ├─ PlayerDataApiFacade
│  ├─ EffectApiFacade
│  └─ CandidateApiFacade
├─ CandidateSetResolver
├─ EffectSpecCompiler
├─ EffectRegistry
├─ EffectTreeExecutor
└─ LuaVisibilityPolicy
```

每次 Lua 调用创建独立 `LuaInvocationContext`：

```text
LuaInvocationContext
├─ eventId
├─ eventType
├─ sourceEffectId
├─ ownerEffectId
├─ attachmentParentEffectId
├─ subscriptionId
├─ respondingPlayerId
├─ responseKind = effects / candidatePatches / none
├─ stateRevision
├─ definitionVersion
└─ permissions
```

API 门面只在该上下文存活期间有效。`attachmentParentEffectId` 是本次 Lua 返回值要挂入的当前结算节点，只由 C# 设置，不向 Lua 开放修改；`responseKind` 限定处理函数本次能返回的结构；`permissions` 决定能读取哪些隐藏数据以及能使用哪些 Effect 或 Candidate 构造函数。

### 4.2 查询 API 的 C# 处理

```text
准备分发 RuleEvent
  → 锁定本次读取使用的 stateRevision
  → 创建 LuaInvocationContext
  → 注入 Global、GameData、PlayerData、Effect
  → Lua 通过查询门面获取只读快照和稳定引用
  → Lua 返回 EffectSpec[]
  → 立即销毁或失效本次 API 门面
```

C# 对查询调用统一执行：

1. 校验当前调用上下文仍有效。
2. 校验稳定 ID、参数类型和筛选字段白名单。
3. 按 `LuaVisibilityPolicy` 剔除隐藏字段。
4. 从同一 `stateRevision` 生成 DTO，再转换为 Lua table 或只读 userdata。
5. 对列表查询设置结果数量、递归深度和调用次数上限。
6. 不把查询行为写入 Effect 链；但开发诊断可以记录 API 名称、耗时和返回数量。

`Global.Map` 应包装现有地图查询服务和运行时地图状态；`GameData`、`PlayerData` 则从新的只读投影器读取。禁止把 `GameState.FindPlayer`、地图定义对象或集合直接注册给 Lua。

### 4.3 候选集构建与补丁处理

`CandidateSetResolver` 是所有需要玩家选目标的 Effect 与固有效果链的统一入口。UI、Lua 卡面和具体命令处理器都不能各自维护一套候选列表。

```text
Effect 准备选择或校验固定目标
  → 按 effectTypeId + candidateKind 选择 CandidatePolicy
  → C# 构建 candidatePoolIds 与 defaultCandidateIds
  → 形成 CandidateSetBuilding Event，responseKind = candidatePatches
  → 按稳定订阅顺序调用 Lua
  → 校验并逐个应用 CandidatePatch
  → 记录补丁来源、顺序和 finalCandidateIds
  → 有选择时创建 InteractionRequest；固定目标时直接检查是否仍在最终集合
```

C# 至少分开以下规则层：

- 候选池上限：稳定 ID 存在、实体类型正确、属于本次 Effect 注册的最大范围，并满足不能被任何卡面绕过的安全和结构约束。
- 基础候选：普通规则在当前状态下默认认可的候选，例如移动城市的相邻、开放和无对手城市条件，或放置影响力的空槽、资源点和公路条件；它可以被 `Candidate.Add` 或其他补丁显式覆写。
- 卡面补丁：显式订阅的 Lua 能力对当前集合执行增加、移除或求交。
- 最终复验：玩家答案到达 Host 时，以最新状态重复前三层，再检查答案和数量约束。

每个 `CandidatePatch` 的来源内容实例、能力 ID、订阅 ID 和应用序号由 C# 补齐，Lua 不能冒充其他来源。`Add` 可以加入候选池上限中被基础候选排除的项目；需要改变候选类型、引用有效性、权限边界或其他硬规则时，仍必须调用 C# 已注册的 `movementMode`、`placementMode` 或另一个 Effect，不能用补丁越过候选池上限。

同一处理器返回的补丁整体校验，任一补丁包含未知 ID、错误候选类型、越界增加或不合法操作时，本处理器的全部补丁都不应用，并使所属候选准备节点进入可诊断故障；不能静默忽略一部分后继续向玩家展示不可信候选。

`CandidateSetBuilding` 只调用订阅索引中“当前实例有效、`candidateKindFilter` 匹配且过滤条件成立”的处理器，不遍历并调用所有企业、角色牌或城市样式 Lua。它不能创建玩家交互或子 Effect，因此正常情况下在单次 Host 调用内同步完成。最终候选和补丁记录写入所属 Effect 或 `InteractionRequest` 节点；恢复 UI 时读取记录，不需要重新运行已经有分发收据的 Lua。若状态已经变化并需要刷新候选，则创建新的候选集版本和新的 Event ID。

### 4.4 Lua 返回子 Effect 的 C# 处理

Lua 调用 `Effect.*` 时，C# 绑定函数只校验构造函数名称和参数 table 的基本形状，并返回带有内部类型标记的 `EffectSpec` userdata；调用构造函数本身不修改状态，也不挂树。Lua 处理器正常返回后，C# 统一处理完整返回数组：

```text
C# 以仍处于结算中的节点创建 RuleEvent 调用上下文
  → Lua 返回连续 EffectSpec[]
  → 校验数组形状、子节点数量、嵌套深度和每个 EffectSpec
  → 根据 EffectRegistry 校验 effectTypeId 与参数 schema
  → 将参数规范化为稳定引用和基础值
  → 以 eventId + subscriptionId + 返回下标 + 嵌套路径生成确定性节点 ID
  → 将最外层每个 EffectSpec 建成 attachmentParentEffectId 的有序子节点
  → 为每个子节点建立默认的“进入成功或失败终态前阻塞父节点”关系
  → Lua Event 调用结束，当前结算节点等待这些子节点
  → EffectTreeExecutor 依次执行子节点
  → 子节点执行前按最新 GameState 再次进行规则校验
  → 原子提交状态与 EffectRecord
  → 创建 UI 子节点、固有效果链子节点或后续 RuleEvent
```

当前结算节点必须在 Lua 分发和子节点挂载完成前保持 `Running` 或等价的“正在收集响应”状态，不能先进入 `Completed` 再向已完成节点补挂子节点。若某个规则语义上的“完成后 Event”允许产生阻塞响应，C# 应先进入完成响应窗口，收集并执行返回的子 Effect，最后才把源节点标记为完成。

同一个 Event 有多个订阅处理器时，C# 先按 Event 既定的处理器顺序调用；每个处理器返回列表的内部顺序保持不变。若规则要求玩家决定多个响应的先后顺序，Event 分发器应先创建无序候选或有限效果轮，不能依赖 Lua 模块加载顺序。

这里有两次不同的校验：

- 编译校验：Lua 返回时检查接口、类型、引用格式、权限和树结构是否合法。
- 执行校验：节点真正运行或玩家回答 UI 后，根据最新权威状态检查资源、目标、阶段、数量和可见性。

Lua 处理器抛错或任一 `EffectSpec` 编译失败时，本次返回的整组子 Effect 都不挂树，避免只接受一部分。节点已经提交规则状态后才发生的表现错误，不回滚规则提交；规则节点根据已经写入的 `EffectRecord` 恢复表现或继续后续子节点。

### 4.5 Effect 注册与固有效果链处理

`EffectRegistry` 为每个稳定 `effectTypeId` 注册：

```text
EffectRegistration
├─ effectTypeId
├─ luaConstructorName
├─ argumentSchema
├─ allowedCallerKinds
├─ executorKind = atomic / intrinsicFlow
├─ validator
├─ executor 或 flowBuilder
├─ resultSchema
└─ completedEventType
```

- `atomic` 由 C# 在一个规则提交边界内完成，例如获得资源、获得分数、旋转设施牌。
- `intrinsicFlow` 由 C# 创建固定子节点并等待，例如移动城市、建设、探索和采集。
- 开放式 `intrinsicFlow` 为每名应答玩家创建独立子任务和一个完成屏障。它不把 Lua 数组的默认顺序解释为玩家执行顺序；多个命令可按到达顺序由 Host 串行提交，直到 `completionPolicy` 满足。采集和不要求玩家顺序的回合开始选择可复用这一结构。
- 任意 Effect 的 `allowDecline = true` 都由 UI 在首次状态提交前提供通用放弃按钮。玩家点击后提交 `DeclineEffect`；Host 接受后记录 `Failed(player_declined)`，不调用具体执行器的提交步骤，也不形成成功语义 Event。失败已是终态，因此解除该节点对父节点的阻塞。
- 固有效果链调用其他 Effect 时必须通过同一个 `EffectRegistry` 和树执行器创建子节点，不能直接调用另一个处理器的方法绕过记录。
- 需要玩家输入时，执行器创建 `InteractionRequest` 子节点并阻塞所属 Effect；Lua 不直接调用 UI。
- 子节点进入成功或失败终态后由树执行器重新判断父节点，不使用独立持久化调用栈。

### 4.6 三个固定 Effect 处理区的 C# 处理

三个固定处理区都遵守“Event 调用 Lua，Lua 返回 Effect式，C# 决定父节点”的规则。它们不是三种新的 Effect，也不允许脚本持有或填写目标节点 ID。

```text
能力定向 Event
  → 调用 effectHandlers.current
  → 返回项挂到该 Event 的 attachmentParentEffectId

玩家收尾窗口 Event
  → 收集该玩家当前有效的 playerCleanup 处理器与待执行 Binding
  → 必要时建立有限效果轮，让该玩家决定先后顺序
  → 逐个调用 Lua，返回项挂到该玩家收尾节点

最终计分窗口 Event
  → 区控计分类别：按稳定玩家顺序完成全员区控
  → 资源计分类别：按稳定玩家顺序完成全员资源计分
  → 卡面计分类别：收集 finalScoring 处理器与 Binding，按稳定玩家和 orderPolicy 调用 Lua
  → 返回项挂到对应计分类别下的玩家节点
```

`TimingHandlerRegistry` 负责两类来源：

- `while_active` 不复制脚本状态。到达时点时，根据权威 GameState 中仍在生效区域的卡面实例及其内容定义枚举处理器。
- `after_resolve_once` 在来源能力成功结算时，把可序列化的 `TimingHandlerBinding` 写入来源 Effect 的记录；运行时注册表可以从 Effect 链重建。即使卡面之后移动区域，也按定义中确定的取消规则判断是否仍执行。

```text
TimingHandlerBinding
├─ bindingId
├─ contentInstanceId
├─ abilityId
├─ handlerSlot = playerCleanup / finalScoring
├─ targetWindowKey
├─ scopedPlayerId
├─ sourceEffectId
├─ capturedArguments
├─ definitionVersion
└─ status = registered / attached / completed / cancelled
```

`capturedArguments` 只能从来源 Event、来源 Effect 的规范化参数或结果中提取已经确认的基础值和稳定引用，不保存 Lua table、闭包、协程或 C# 对象引用。窗口 Event 的当前数据仍由 handler 通过 `event`、`Global`、`GameData` 和 `PlayerData` 查询。

固定处理区也要占用稳定的处理器键：持续处理器可由 `contentInstanceId + abilityId + handlerSlot` 生成，一次性处理器使用 `bindingId`。C# 将这个键写入 `LuaInvocationContext.subscriptionId` 或后续重命名后的统一 `handlerInvocationKey`，使固定处理区与普通 Event 订阅使用相同的节点 ID 和幂等规则。

一次性 Binding 的调用键由 `bindingId + targetWindowNodeId` 确定。C# 应把“处理函数返回列表已成功编译并挂树”的收据和子节点 ID 在同一提交边界内写入：恢复时若状态已经是 `attached`，只继续已有子节点，不再次运行 Lua；返回空列表时可以直接标记 `completed`，返回非空列表时等所有已挂子节点进入终态后再标记 `completed`。

处理器顺序不能依赖 Lua 文件或模块的加载顺序。玩家收尾阶段沿回合主链既定的玩家顺序进入；同一玩家同时拥有多个允许自行排序的收尾处理器时创建有限效果轮。最终计分的类别顺序固定为“全员区控 → 全员资源 → 卡面计分”；每个类别内部使用稳定玩家顺序，卡面计分再按卡面实例 ID、能力 ID 和 `orderPolicy` 排序。若具体规则允许玩家选择，再显式创建 UI 交互节点。

### 4.7 幂等、版本和动态结果

- 子节点 ID 由 `eventId`、`subscriptionId`、返回数组下标和嵌套路径确定；同一次 Event 以相同处理器和相同返回顺序恢复时得到相同 ID。
- C# 记录某个 `eventId + subscriptionId` 是否已经成功编译并挂载返回列表。已挂载时不得再次执行 Lua 生成第二份子树。
- Effect 节点记录规范化后的参数、结果、调用内容版本和提交序号，不保存 Lua table、闭包或协程。
- 随机数、抽牌、洗牌和玩家输入由 C# 记录实际结果。需要根据结果继续时，C# 发布新的 RuleEvent，并以原 Effect 节点作为 `sourceEffectId`。
- Lua 定义版本与本局 `contentVersion` 不一致时拒绝运行；不能静默使用更新后的脚本恢复旧对局。

### 4.8 当前 C# 数据模型需要补充的内容

| 当前情况 | 需要补充 | 原因 |
| --- | --- | --- |
| `InfluencePlacement` 只有 `PlayerId` | 增加稳定 `influenceId`、可空的 `RuleSubjectRef ownerSubject` 和来源引用；迁移期把旧 `PlayerId` 作为玩家归属投影 | 支持企业、角色和无归属影响力，并允许移动同一影响力实例 |
| `GameState` 没有本局 DLC 与内容版本快照 | 增加 `GameConfigurationState`，保存地图、玩家数、启用 DLC、内容版本或哈希 | `GameData` 必须查询本局固化配置，而不是当前安装内容 |
| 企业与科室板尚无通用运行状态 | 增加企业实例、各玩家等级、解锁特效和当前科室板状态 | 支持 `GetActiveEnterprises` 与 `GetCurrentDepartment` |
| 多处卡牌状态只保存字符串卡牌 ID | 区分 `definitionId` 与稳定 `instanceId` | 同名或重复卡牌不能只靠定义 ID 定位，Effect 链也需要实例级引用 |
| 当前待选状态分散为多种专用字段 | 逐步投影到通用 `InteractionRequest` 与 Effect 子节点 | 让 Lua API 使用统一阻塞和恢复机制 |
| 当前没有通用 Effect 注册表与树执行器 | 新增 `EffectRegistry`、`EffectSpecCompiler` 和 `EffectTreeExecutor` | 所有 `Effect.*` 必须走统一校验、记录和完成判定 |
| 当前没有固定时点处理器和一次性延迟登记 | 新增 `TimingHandlerRegistry` 与可序列化的 `TimingHandlerBinding` | 支持卡面能力在玩家收尾或最终计分时生成 Effect，同时保证恢复时不重复调用 Lua |
| 当前目标候选由多个查询服务和 UI 协调器分别生成 | 新增 `CandidateSetResolver`、`CandidatePolicyRegistry` 和候选补丁记录 | 让城市移动、影响力、卡牌等候选统一接受卡面增删并在 Host 提交时复验 |

现有 `GameState.Round`、`ActionRound`、`CurrentPlayerId`、玩家资源和城市位置可以先作为查询投影的数据源；但 API 返回结构应直接采用目标模型，避免 Lua 脚本绑定迁移期字段。

### 4.9 现有卡面效果实现的迁移边界

当前角色牌、城市样式和设施牌入场效果虽然已经形成可运行闭环，但它们建立在“C# 按具体卡面 ID 分支、专用待选状态、专用查询服务和专用 UI 协调器”之上。目标架构改为“Lua 定义具体卡面并组合 Effect，C# 只提供通用规则原语、固有流程、候选解析、UI 交互和树调度”后，这些实现不能原样注册为新 Effect 执行器，需要大范围改写和重构。

现有实现仍有三类价值：

- 牌面数值、目标范围、执行顺序和失败语义可以作为 Lua 内容录入的规则参考；
- 已经相对独立的原子领域操作可以在去除具体卡面分支后，改造成 `EffectRegistry` 背后的 C# 执行器；
- 现有测试可以改造成迁移后的黑盒规则回归，验证相同输入仍产生相同规则结果。

主要迁移范围：

| 当前实现区域 | 目标形态 | 重构要求 |
| --- | --- | --- |
| `CharacterCardDatabase`、`CharacterCardDefinition` | Lua `CharacterCardDefinition` 内容注册 | C# 不再枚举并硬编码具体角色牌策略、计谋；仅校验定义结构和稳定能力 ID |
| `CharacterCardService` 及各角色专用分支 | `CharacterEffectActivated` 定向 Event → Lua Effect式 → 通用 Effect 执行器 | 删除按角色牌 ID 分流具体规则的核心职责；保留角色牌翻开、使用限制、移动区域等通用流程 |
| `CharacterCardOptionQueryService` 与角色专用地图候选 | `CandidatePolicyRegistry` + `CandidateSetResolver` | 基础规则由 C# 生成，具体卡面限制由已注册 Lua 订阅返回补丁，不让 UI 或角色服务另算一套候选 |
| `CityStyleDatabase`、`SpecialActionDatabase` | Lua 城市样式定义、玩家标记区和特殊行动能力 | 图案匹配、标记区结构等通用数据仍由 C# 校验；具体奖励、费用与特殊行动 Effect式迁入 Lua |
| `DeclareCityStyleService` | `Effect.DeclareCityStyle` 固有流程 | 保留匹配、设施占用、标记与分数等通用规则步骤；宣告即时效果通过定向 Event 调用对应 Lua |
| `SpecialActionService` 及专用 pending step | `CityStyleSpecialActionActivated` → Lua Effect式 | 行动预算、使用次数和标记移动由固有流程管理；不同样式的支付、移动、影响力等内容不再写在 C# 分支中 |
| `FacilityEntryEffectService`、`FacilityInfluenceEffectService` | `FacilityEntryEffectActivated` 定向 Event → Lua Effect式 | 设施牌具体入场效果迁入 Lua；C# 只保留建设固有链、通用 Effect 和必要的原子事务 |
| `PendingCharacterEffect`、`PendingSpecialAction`、设施专用待选会话 | `InteractionRequest` + Effect 子节点 | 待选状态、答案、阻塞和恢复统一进入 Effect 树，避免每增加一张牌就扩展 `GameState` 专用字段 |
| 角色牌、城市样式与设施效果的专用 UI 协调器 | 通用交互渲染器加少量表现适配 | UI 根据 `interactionTypeId`、候选和答案 schema 展示，不再决定具体牌面规则或直接串联领域服务 |

迁移期间必须遵守以下边界：

- 同一个具体卡面能力只能有一个权威实现。迁到 Lua 后必须停用对应 C# 卡面分支，不能两边同时结算。
- 可以用适配器把旧服务暂时包装为某个通用 Effect 执行器，但适配器不得继续接受具体卡面 ID 并在内部扩展新分支。
- 不要求一次性重写全部内容。应先完成 Effect 树、Event、候选集和 `InteractionRequest` 内核，再分别选择一张角色牌、一种城市样式和一张有待选入场效果的设施牌打通纵向样板，最后按内容类型迁移其余卡面。
- 旧专用待选字段只有在所有读写方迁移并完成存档兼容处理后才能逐项移除；迁移期间由兼容投影保持旧 UI 或旧快照可读，不能让旧状态机和新 Effect 树各自推进同一流程。
- 现有单元测试不得只因为实现被替换而删除；应优先改写为对命令结果、Effect 记录、Event 次数、候选范围和最终 `GameState` 的行为断言。

迁移完成的最低判定是：新增一张同类型角色牌、城市样式或设施牌时，只需增加 Lua 定义、脚本和内容资源，不需要修改 C# 卡面分流、增加专用 `GameState` 待选字段或编写新的专用 UI 流程。

### 6.3 移动城市 Event 与事件牌检测顺序

`BeforeCityMove` 位于目标选择之前。它用于让 Lua 在一次移动城市开始时追加前置 Effect；如果能力只需要增加或减少目的地，应订阅之后的 `CandidateSetBuilding` 并返回候选补丁，不应通过 `BeforeCityMove` 直接传候选。

移动城市是否需要翻开事件牌不属于 C# 内置移动链，由 `CityMoveCompleted` 的 Lua 订阅检测。推荐顺序为：

```text
BeforeCityMove（Lua 可返回移动前子 Effect）
  → 前置响应全部完成
  → 建立移动目的地候选
  → CandidateSetBuilding（Lua 只能增删候选）
  → 玩家确认目标或复验固定目标
  → 提交移动城市位置
  → 依次调用 RemoveInfluence 清除规则指定的影响力
  → 调用 PlaceInfluence 处理出发地影响力
  → CityMoveCompleted
      → Lua 检查目标地块是否已有资源点指示物，以及本次移动是否应触发事件
      ├─ 需要：返回 RevealEventCard，指定 resourcePoint 并启用指示物放置
      └─ 不需要：返回空 Effect式
  → CityMoveCompleted 的响应子树完成
  → MoveCity 节点最终完成
```

这里的 `CityMoveCompleted` 表示移动城市的内核步骤完成并形成规则事实，不表示它的 Lua 响应已经结束。Event 发出后，`MoveCity` 节点仍等待该 Event 产生的阻塞子树；事件牌结算完成后才进入最终 `Completed`。不另行暴露只改变停靠位置的 `Effect` 或中间位置 Event。

城市移动清除对手影响力时，因为流程显式调用 `RemoveInfluence`，每个成功清除都会形成 `InfluenceRemoved`。`MoveInfluence` 只改变同一影响力实例的槽位，不形成内部的 `InfluenceRemoved`/`InfluencePlaced`。`ReplaceInfluence` 则确实调用移除与固定原位置放置两个子 Effect，因此会依次形成 `InfluenceRemoved`、`InfluencePlaced`，外层完成时还可形成 `InfluenceReplaced`。

## 8. 通用数据结构草稿

本节只在逐项 API 暴露出共同字段后再提取，避免先设计过大的统一协议。

### 8.1 `RuleEvent`

```text
RuleEvent
├─ eventId
├─ eventType
├─ sourceEffectId
├─ ownerNodeId
├─ routeKey
├─ targetEntityId
├─ playerId
├─ payload
├─ responseKind = effects / candidatePatches / none
├─ stateRevision
├─ sequence
├─ definitionVersion
└─ visibility
```

`eventId` 必须能由来源节点和语义时点稳定生成；`ownerNodeId` 是 Event 响应所阻塞或附着的流程节点，`sourceEffectId` 是产生事实的 Effect，两者可能相同也可能不同。`payload` 在进入 Lua 前按 `visibility` 投影，不能因为脚本运行在 Host 就暴露隐藏牌面。

### 8.2 `EffectSpec` 与 Lua 返回结果

```text
EffectSpec
├─ effectTypeId
├─ normalizedArguments
├─ executionOptions
│  ├─ allowDecline
│  ├─ decisionPlayerId
│  ├─ declinePromptKey
│  └─ unavailablePolicy
└─ nestedEffectExpressions

LuaEffectHandlerResult
└─ effects[] = 连续有序的 EffectSpec 数组

EffectNodeResult
├─ status = completed / failed
├─ failureReason
└─ normalizedResult
```

`EffectSpec` 是 Lua 构造函数产生的临时描述，不包含节点 ID、父节点 ID 或 Blocker。C# 编译返回结果时，使用当前 `LuaInvocationContext.attachmentParentEffectId` 建立实际子节点，并用 Event、订阅和数组路径生成稳定节点 ID。

Effect 被玩家放弃后进入终态 `Failed`，并记录 `failureReason = player_declined`、决定玩家和回答请求 ID。`Completed` 和 `Failed` 都属于“已经完成结算”的终态，都会解除父节点等待；条件式等父节点可以读取子节点结果，决定是否创建后续子节点。脚本异常、数据损坏等不可继续的内核故障应使用独立 `Faulted` 状态，不能混入规则失败。

### 8.3 `InteractionRequest`

```text
InteractionRequest
├─ requestId
├─ interactionTypeId
├─ ownerEffectId
├─ answeringPlayerId
├─ visibility
├─ promptKey
├─ candidateSetId
├─ candidateSetVersion
├─ candidateIds
├─ minSelections
├─ maxSelections
├─ allowDecline
├─ answerSchema
├─ status = open / answered / cancelled / invalidated
├─ normalizedAnswer
└─ answeredAtRevision
```

交互请求是 Effect 树中的可恢复阻塞对象。关闭界面不改变 `status`；只有 Host 接受合法答案、规则明确允许的取消，或候选永久失效后按失败策略处理，才能解除对应 Blocker。

```text
CandidateSetDraft
├─ candidateSetId
├─ version
├─ candidateKind
├─ sourceEffectId
├─ executingPlayerId
├─ candidatePoolIds
├─ defaultCandidateIds
├─ currentIds
└─ context

CandidatePatch
├─ operation = add / remove / intersect
├─ candidateIds
└─ reasonCode

AppliedCandidatePatch
├─ subscriptionId
├─ sourceContentInstanceId

├─ applySequence
├─ normalizedPatch
└─ resultingCandidateIds

CandidateResolutionRecord
├─ candidateSetId
├─ version
├─ stateRevision
├─ candidatePoolIds
├─ defaultCandidateIds
├─ appliedPatches
└─ finalCandidateIds
```

Lua 只创建 `CandidatePatch`；其来源、应用序号和每一步结果由 C# 填写。`CandidateResolutionRecord` 可以随所属 Effect 或 `InteractionRequest` 保存，使重连恢复使用相同候选，不依赖再次执行 Lua。

### 8.5 固有效果链描述

固有效果链在 Lua 侧仍使用普通 `EffectSpec`，不另设 `IntrinsicFlowRequest`。C# 根据 `EffectRegistry.executorKind = intrinsicFlow` 识别它，并由对应 `flowBuilder` 创建固定子节点。

开放玩家任务组额外使用可序列化的组状态：

```text
OpenPlayerTaskGroupState
├─ groupId
├─ ownerEffectId
├─ completionPolicy = all_required / required_count
├─ revealPolicy = immediate / after_all
├─ tasks[]
│  ├─ taskId
│  ├─ playerId
│  ├─ childEffectIds[]
│  ├─ required
│  └─ status = pending / running / completed / failed
└─ status = open / completed / faulted
```

组内“任意顺序”只表示多个玩家可以同时看到待办并以任意顺序提交，不表示 C# 并发写 `GameState`。Host 仍以命令提交序号逐条复验和提交；`revealPolicy = after_all` 时先分别保存遮蔽答案，等完成屏障满足后再统一公开并生成后续 Effect。

### 8.6 固定处理区与 Lua Event 订阅声明

```text
ContentAbilityDefinition
├─ abilityId
├─ effectHandlers
│  ├─ current
│  ├─ playerCleanup
│  └─ finalScoring
└─ eventSubscriptions[]

EffectHandlerDefinition
├─ handler
├─ activationPolicy
├─ scope
├─ cancelPolicy
└─ orderPolicy

EventSubscriptionDefinition
├─ subscriptionId
├─ eventType
├─ handler
├─ routeOrFilter
├─ responseKind
├─ candidateKindFilter
├─ activationPolicy
└─ orderPolicy
```

固定处理区用于当前结算、玩家收尾和最终计分三个高频规则时点；`eventSubscriptions` 只声明其他规则时机。两者在运行时都由 Event 唤起，并共享同一套 Lua 调用、`EffectSpec` 编译、挂树、阻塞和幂等机制。
